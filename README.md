# 抖音 AI 搜：长程出行任务助手

日期：2026-09-05 · 方案更新

产品方向：将 AI 搜升级为能持续执行复杂任务的助手，先打穿国内机票与酒店的联合规划和预订链路。

本文是产品与技术建议，不代表已上线能力或官方路线图。接口覆盖、成本和实验指标需内部验证。

## 核心目标：从提出需求到行程落实

用户提出“帮我安排出差”，系统持续查找、比较、调整，并推进到预订完成。用户中途离开、隔天回来，任务可以接着做；某一步失败，已完成的部分不会丢失。

长程能力的价值，在于跨步骤、跨时间和跨工具可靠地完成目标，而非仅延长模型思考时间。

首发场景：国内单人往返机票＋单城市酒店。后续再扩展多人、多城市及改签退订。

## 标志性体验：一句话安排出差

示例需求：“下周二去上海出差，周四回来，从北京出发，住公司附近，总预算 4000 元，帮我安排。”

以下为体验设计示例，不代表真实报价、库存或实际订单。

| 阶段 | 系统动作 | 用户看到什么 |
|---|---|---|
| 明确约束 | 将相对日期转为明确日期，确认公司地址、到达时间和必要偏好 | 集中补齐关键缺失信息，避免反复追问 |
| 联合规划 | 同时查航班和酒店，计算交通时间与总费用 | 省钱、方便、舒适等少量可比方案 |
| 深入核查 | 核验房型、退改、行李、税费和实时可售状态 | 总价、限制条件、推荐理由与核价时间 |
| 持续调整 | 用户要求晚一点出发或换酒店，重算相关安排 | 保留已有约束，标出受影响部分 |
| 准备预订 | 选定航班房型，使用已授权的旅客信息准备订单 | 最终订单清单、价格和待确认事项 |
| 完成与跟进 | 经确认执行支持的预订步骤，获取真实回执 | 订单状态、失败原因和下一步操作 |

## 产品形态：一张持续推进的任务页

任务页始终呈现目标与预算、当前方案、进度、待确认事项以及订单状态。对话负责表达需求，任务页负责呈现真实执行状态。

用户修改条件时，仅重算受影响的步骤。修改时间可能影响入住日期，修改机场可能影响地面交通；已确认或已出票的订单必须明确标记，不能静默替换。

后台执行只在完成、失败、价格或库存实质变化、需要用户操作时通知。对同一任务可以暂停、恢复和取消待执行步骤；取消任务不等于取消已经成立的订单。

支付及不可逆的订单操作由用户明确确认，并在供应商支持的授权范围内执行。

## 技术架构：规划与执行分离

总体链路：理解需求 → 结构化任务状态 → 联合搜索与规划 → 实时核价 → 用户确认 → 订单执行 → 回执核验与恢复。

### 任务状态机

保存目标、硬约束、偏好、候选方案、证据时间、用户确认和订单状态。聊天记录作为输入，结构化任务状态作为执行依据。

建议状态包括：待补充、查询中、待选择、待核价、待确认、执行中、部分完成、已完成、需处理、已暂停。每次状态迁移持久化，并记录对应工具结果。

### 联合约束规划

同时优化航班、酒店及地面交通。显式区分硬约束与软偏好；无法满足预算或时间时，说明冲突并提出最小调整。

时间、总费用和可售性使用确定性校验；模型负责理解偏好、提出候选和解释取舍。跨日到达、入住日期与交通缓冲必须校验。

### 可靠的工具执行层

优先对接供应商接口，拆分查询、核价、创建订单、支付、查单与取消等工具。工具结果标准化，保留供应商原始订单标识和状态。

预订使用幂等机制防止重复下单。请求超时先查订单状态，再决定是否重试；状态未知时进入待核验，不能报告成功或直接再次购买。

### 长程恢复

通过持久化任务队列、检查点和事件记录支持后台执行。登录、库存、价格或授权失效时，只恢复必要步骤，并重新核验关联约束。

机票成功但酒店失败时，展示部分完成状态，优先寻找替代酒店。不得在未获授权时取消已成功订单；跨供应商无法保证原子提交，应明确部分成功的处理流程。

## 抖音差异化：选得明白，订得省事

航班时间、房型库存、价格与退改政策使用实时供应商数据；酒店周边、环境和体验可由相关视频辅助判断。

视频需标记对应酒店、房型及拍摄时间。作者口述、可观察画面和系统推断分别处理，避免将旧视频体验当作当前服务承诺。

将内容发现、证据比较和任务执行连接起来。内容能力增强选购判断，交易接口保证预订真实可完成。

## 接入边界与产品承诺

| 接口覆盖 | 可以承诺的体验 | 完成判据 |
|---|---|---|
| 查询与跳转 | 完成规划并带到预订渠道 | 查询结果有效、跳转目标准确 |
| 核价与订单准备 | 准备可确认的预订方案 | 价格、可售性与关键条款已核实 |
| 创建订单与回执查询 | 在授权范围内帮助完成预订 | 获取真实订单回执并核验状态 |
| 售后接口 | 在支持范围内协助改签退订 | 用户确认费用和影响，获取处理回执 |

第一阶段必须验证供应商覆盖、访问权限、限流、库存更新、订单幂等和查单能力。不能以模型输出或工具请求已发出作为预订成功依据。

旅客信息按最小必要范围授权和使用，敏感字段不进入普通任务日志。公开页面不包含真实旅客或订单数据。

## 分阶段落地

| 阶段 | 核心交付 | 验收重点 |
|---|---|---|
| 第 1—2 周 | 供应商能力盘点、任务定义、真实失败案例与基线 | 明确能执行到哪一步及完成判据 |
| 第 3—6 周 | 联合查询、约束规划、可比较方案、实时核价 | 约束满足、价格一致性、结果可售性 |
| 第 7—12 周 | 用户确认、支持渠道预订、回执核验、部分失败恢复 | 端到端完成、无重复订单、状态可追溯 |
| 第 4—6 月 | 后台恢复、持续跟进、更多场景与供应商 | 跨时间执行稳定性、自然复用和单位成本 |

先以沙箱及测试订单验证异常路径，再在明确授权和供应商规则下小流量上线。覆盖超时、价格变化、库存耗尽、支付未完成、重复回调和部分成功等情况。

## 衡量真正的长程能力

北极星指标：成功完成出行任务的用户数。按接口可支持的范围分层统计，避免将规划完成与预订完成混算。

| 指标 | 定义与关注点 |
|---|---|
| 端到端任务完成率 | 在约定目标及授权范围内完成任务的比例 |
| 用户介入次数 | 区分必要确认与系统失败导致的额外操作 |
| 重复订单率 | 幂等与查单机制的关键护栏 |
| 报价一致性 | 比较展示、确认与实际订单价格，记录变化原因 |
| 失败恢复成功率 | 可恢复失败中最终完成的比例 |
| 状态准确率 | 页面状态与供应商订单状态一致 |
| 单次成功任务成本 | 综合模型、检索、供应商与运行成本 |

先测基线再定提升目标。上线实验同时检查退款投诉、取消损失和人工客服负担，防止以增加用户后续处理成本换取表面完成率。

## 优先决策

第一笔资源投向“机票＋酒店联合规划、可靠预订执行与回执核验”。以一个完整出行任务验证长程能力，再扩大场景范围。

先确定交易接口能覆盖到哪一步，再决定产品承诺。让每一步真实发生、能够恢复、结果可核实，成为这一轮产品与技术升级的核心。
